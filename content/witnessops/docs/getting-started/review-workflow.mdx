# Review workflow

The current paid review is [Agent Action Security Review](/review/request?offerId=agent-action-security-review) at €2,500 excluding VAT. Delivery timing agreed in the signed statement of work. It examines one consequential agent or automation action. The operating mode is read, inspect, reconstruct and report. It does not execute the action, change production, remediate, monitor continuously or certify that an agent is safe.

The sequence below is the historical delivery record for the `public_exposure_review` profile. It is not a current sales path and it is not the Agent Action Security Review. It is not a penetration test.

If you are evaluating the request path, read the [Buyer path](/docs/getting-started/proof-run-buyer-path) before submitting work.

## 1. Historical public_exposure_review sequence

The review follows these steps:

1. **Request** — submit a non-secret fit check.
2. **Scoped review** — agree authority, target, approved checks, exclusions, timing, stop conditions, price, and evidence handling before work starts.
3. **Evidence collection and review** — perform only the approved low-impact, unauthenticated checks within the signed target schedule. Preserve source records, hashes, unknowns, and limitations; manually validate, deduplicate and prioritise findings.
4. **Report and handover** — deliver the external attack-surface map, evidence-backed findings, remediation priorities, executive report, technical appendix and explicit unknowns, together with the scope and stop-condition record, evidence manifest and artifact hashes. Include one focused retest of reported findings within 30 calendar days of initial report handover.
5. **Focused retest** — retest the agreed reported findings once within 30 calendar days of initial report handover.

Delivery timing is agreed in the signed statement of work. Mailbox confirmation is not review start, and payment alone does not authorise testing. A signed receipt and offline verifier are included only where the supported path is produced; they are not unconditional deliverables of every review.

## 2. Start conditions

Before target-facing work begins, the engagement needs:

- written authority from the named approving authority
- accepted scope for one authorized public-facing system and a frozen target schedule
- an approved low-impact check schedule
- explicit exclusions and stop conditions
- an approved observation window
- agreed evidence handling and required inputs
- full payment and confirmed operator capacity

Do not send credentials, private keys, API keys, session tokens, recovery codes or other secrets at any stage. The initial request must also exclude logs, screenshots and customer evidence. Only approved, non-secret source material may be shared after scope, authority and secure handling are agreed; customer-data collection remains outside this review.

## 3. Conditional receipt-profile package

Where the supported receipt-profile path is produced, its technical package includes a receipt, evidence manifest, producer verification result, report, staged evidence, normalized records, and comparison result. A public key is present when signed. This describes that package format; it does not promise a signed package for every engagement or establish production signing authority.

For that path, the producer preserves skipped, failed, partial, or inconclusive states in the pre-signing review/comparison result. This is producer output, not an independent verifier verdict. Claim evidence references use IDs precomputed by the OffSec adapter for staged source artifacts and then carried into the proof-engine manifest. They are not invented labels. See [Evidence Bundles](/docs/how-it-works/evidence-bundles).

This conditional external-review package is not a standard deliverable of Agent Action Security Review.

## 4. Public verification boundary

Use [Verify a receipt](/verify) for supported receipt JSON. For the existing `public_exposure_review` receipt profile, which retains the former Public Exposure Review name for technical continuity, the page checks the exact workflow profile, required claims, limitations, timestamps, manifest-digest syntax, and signature syntax.

The result remains `indeterminate` while the request, authority, workflow execution, manifest and artifact bytes, evidence support, signature, and production key authorization have not been independently checked. The page rejects caller-supplied evidence and trust material.

## 5. What remains outside proof

Neither the receipt nor a verified package proves that the system is secure, no vulnerability exists, source tools were correct, capture hosts were uncompromised, human judgment was right, or anything outside the approved scope was checked.
